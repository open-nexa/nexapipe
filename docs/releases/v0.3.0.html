What's new

0.3.0 follows 0.2.0, released 28 September 2026. Nothing in it breaks a working configuration: with no [admin] section the server binds nothing extra and behaves exactly as 0.2.0 did.

Instance health, metrics and state

  • A second, loopback-only listener, off until [admin] listen_addr is set. It forwards nothing: it answers questions about this instance.
  • GET /healthz returns 200 ok for as long as the process is serving — unauthenticated, and nothing else.
  • GET /metrics, behind [metrics] enabled = true, serves Prometheus text format. It is written by hand, so no prometheus dependency was added and the lockfile is untouched. When metrics are off the path is a 404, so a scraper can tell "disabled" from "no traffic yet".
  • A management surface, GET /v1/{status,routes,clients,connections,health}, behind a bearer token that the server generates into <config>.admin-token on first start. There is deliberately no token key in the config: a credential in the file you edit, copy and commit is the thing this design avoids. No token means 503, not an open door.
  • nexapipe status reads those same endpoints from the command line (--json for the raw shape), so the running server stays the single source of truth about its own state.
  • One id per request: 32 hex digits, generated at the entry point rather than per connection. It ends the request's access line and goes back to the client as x-request-id, so a bad answer can be reported with the line that produced it. The same id sits on a request span, with the method, URI and status filled in as they become known.

Turning it on

# config.toml
[admin]
listen_addr = "127.0.0.1:9090"

[metrics]
enabled = true

# then
curl -s http://127.0.0.1:9090/healthz
curl -s http://127.0.0.1:9090/metrics | grep connections_by_path
curl -s -H "Authorization: Bearer $(cat config.toml.admin-token)" \
     http://127.0.0.1:9090/v1/status | jq
nexapipe status --json
Loopback only, and there is no escape hatch. A non-loopback bind is refused at startup rather than warned about: the answers name your routes, clients and backends. Reach it from another host over an SSH tunnel, not by widening the address.

Android: the app asks before it hands over a secret

  • The TOTP secret of an endpoint, its otpauth export, and any change to the relay configuration now go through Android's own confirmation — a biometric where the device has one, the screen-lock credential otherwise. SecretStore already sealed them at rest; what was missing was anything asking before handing them back.
  • One confirmation covers the next two minutes, so pointing the app at a relay is not three prompts in a row.
  • A device enrolled with neither a biometric nor a screen lock is refused rather than quietly downgraded, and the way to enrol one is a tap away.
  • Starting and stopping the proxy is deliberately not gated: the VPN has to come back by itself after a reboot, with nobody there to confirm anything.
Not yet confirmed on a device. Everything past BiometricPrompt itself has been compiled, unit-tested and linted, but not watched running. If a prompt misbehaves on your device, that is the part to look at first — and the desktop app has no such gate yet; it is planned for 0.4.

Changelog

Added

  • The auxiliary listener and everything above it: /healthz, /metrics, the token-guarded /v1/* endpoints, and nexapipe status.
  • A request ID: 32 hex digits per request, on its access line, on the response, and on a request tracing span that also carries the method, URI and status.
  • Android: a prompt in front of the credentials the app holds, described above.
  • docs/iroh-boundaries.md — what still touches third-party infrastructure whatever relay_mode says. The two READMEs now point at it instead of repeating a caveat.
  • CHANGELOG.md. 0.2.0 shipped without one, so its entry is retrospective; 0.3.0 is the first release written into it as it happened.

Changed

  • Hot-reload rules are one table in both READMEs: what a config reload applies, and what needs a restart. They used to be scattered across the configuration sections.
  • The access log line ends with id=<hex>. It is appended rather than inserted, so every field before it keeps its column and a script that splits on spaces finds the host, the status and the duration where it did.
  • HTTP responses carry x-request-id. A backend that sends its own is dropped rather than duplicated, so there is one id to quote and it is ours. L4 flows and TLS passthrough are tunnels, not requests: they get an id on the access line and the span, and have no HTTP response to put a header on.

Fixed

  • Both READMEs quoted the iroh version wrongly in two ways at once: it is declared ^1.0.1, not pinned, and the lockfile resolves 1.2.0. docs/iroh-boundaries.md states it correctly and both READMEs defer to it.

Before upgrading

Coming from 0.1.x rather than 0.2.0? default_backend was removed in 0.2.0 and the server refuses to start on a config that still names it — refusing is the point, since ignoring it would quietly turn forwarding into 404s. Replace it with a catch-all route, host_pattern = "*".
  • Nothing changes by default: with no [admin] section the auxiliary listener is not bound, and no extra port is held open.
  • Desktop: bundles are signed, so an in-app update from 0.2.x verifies as usual through latest.json.
  • Android: enroll a screen lock if you never did. Without a biometric or a screen lock the credential screens refuse to open at all, because there is nothing for the app to authenticate against.
