Release

NexaPipe 1.2.0

A minor release. It opens one new thing on the client — a ticket that does not go stale — and it changes one default on the server: nothing configured now means one fixed relay rather than every N0 relay with a home relay chosen by latency, because a relay that migrates drops the connections routed through it. Nothing has to be enrolled again — the handshake, the ALPN and the L4 preface are unchanged on the wire, so a 1.1.1 client talks to a 1.2.0 server and the other way round.

5 November 2026 · one tag ships the server archives, the desktop bundles, the Android APK and the container image.

Downloads

Client app first, then the server. Nothing needs an account, and nothing is gated.

The macOS and Windows desktop bundles are published unsigned.
  • macos — the .dmg and the .app inside it carry no Developer ID signature and are not notarized. macOS Gatekeeper refuses them until the user allows them by hand.
  • windows — the NSIS installer (-setup.exe) carries no Authenticode signature. Windows SmartScreen refuses it until the user allows it by hand.

A code signature costs money — the Apple Developer Program is $99 a year and a Windows certificate is bought per year on top of that — and this project has no revenue, so the desktop bundles ship without one. Everything else is signed: the Android APK carries the release keystore, the server archives carry a checksum, and the container image is signed with the release key and carries a provenance attestation.

On macOS the refusal is the strict one: the app does not open until the user chooses “Open Anyway” in the dialog, which is a click in System Settings → Privacy & Security. The Tauri updater’s own signature is separate from the operating system’s and is produced when the release build runs with its signing key, so an update installs the same way as the first install does whenever the release carried one.

Container image

Published with everything else, as one multi-arch manifest for linux/amd64 and linux/arm64. Both READMEs carry a systemd unit for the server now as well.

# This release exactly
docker pull ghcr.io/open-nexa/nexapipe:1.2.0

# The newest stable release (:latest never points at a pre-release)
docker pull ghcr.io/open-nexa/nexapipe:latest

docker-compose.yaml names the published image, so docker compose up pulls it rather than building — --build still builds locally under the same name.

The image runs as uid 1000, not root. The three mounted directories have to be writable by that uid, so run sudo chown -R 1000:1000 config secrets logs before the first start of an upgraded deployment. Without it the iroh.key cannot be opened and is regenerated — a new Node ID, and every client stops finding the server. See before upgrading.

What's new

1.2.0 follows 1.1.1. It opens one new thing on the client — a ticket that does not go stale — and it changes one default on the server: nothing configured now means one fixed relay rather than every N0 relay with a home relay chosen by latency. No protocol, ALPN or L4 preface changes, so a 1.1.1 client talks to a 1.2.0 server and the other way round, and nothing has to be enrolled again.

A ticket that does not go stale

  • An ordinary ticket carries an address, and an address carries two things with very different lifetimes: the Node ID, which is the endpoint's public key and changes only if the secret key changes, and the addresses — the relay URLs and the IP addresses — which change whenever the host moves, the socket gets a new port, or the home relay migrates.
  • The addresses are what make an ordinary ticket go stale, and a stale ticket is worse than no ticket: it sends the client to an address that no longer answers. That is why deployments end up carrying a bare Node ID instead — and why a Node ID alone has to wait for an address lookup before the first packet can go anywhere.
  • A stable ticket is the Node ID plus exactly one relay URL and no IP addresses at all. iroh does not wait for an address lookup when it already knows any path, so a client holding this ticket starts its handshake at once instead of after a DNS and pkarr round trip — which, in a network where those lookups are slow or blocked, is the difference between a connection and a timeout.
  • The lookup still runs, and its result is merged into the path set when it arrives: the direct addresses the peer publishes are still used and hole punching still happens. The ticket removes the wait, not the possibility of a direct path.
  • The server prints one at start-up beside the ordinary ticket — Stable ticket (does not go stale) — and says so when the relay mode pins no relay, in which case the ticket is the Node ID alone.

Nothing configured means one fixed relay

  • iroh's own default is every N0 relay with the home relay chosen by latency, and it may migrate between them — and every migration drops the connections routed through it, a WebSocket in particular.
  • The server and the CLI's --local-proxy were the two endpoints left migrating: the local proxy resolved “nothing configured” to no mode at all and handed the endpoint to iroh's default.
  • Both resolve to pinned now, the same default the desktop app and the Android client already used — and a fixed relay is also what makes the stable ticket name a relay the endpoint stays registered at.
  • A configuration that names a mode explicitly is unaffected: default still means every N0 relay, and custom still means the one relay the operator runs.

A Node ID and a ticket can be configured together

  • The Node ID is the identity and the ticket's addresses are the paths. Before, a configured Node ID won and the ticket was ignored entirely — so a ticket that carried the path was thrown away in favour of the bare Node ID, and the client was back to waiting for a lookup.
  • A ticket whose Node ID disagrees with the configured one is refused now, with the two names in the message, rather than resolved in favour of either: a ticket for the wrong endpoint reaches the wrong endpoint, and no amount of address fixing repairs that.
  • A blank ticket field is no ticket at all — a template or an unset placeholder leaves server_ticket = "" around a node ID that was working before the field existed — and a ticket field holding a bare Node ID still works.

The desktop can offer IPv6 candidates, and does not by default

  • The endpoint was bound IPv4-only, because on a host whose IPv6 exists but cannot carry full-size QUIC datagrams (PPPoE: v6 MTU 1480, ICMPv6 “packet too big” filtered) iroh's net report calls v6 usable and path migration moves traffic onto it — where every datagram above the real MTU fails, which reads as a connection that dies a few seconds in.
  • The IPv4-only bind is still the default; the new useIpv6 setting turns the IPv6 socket on, which puts IPv6 candidates in the set hole punching offers. That set is the one the server and the Android app already publish, so turning it on makes the desktop's direct path the same shape as theirs.
  • It is off by default because a configuration written before the setting existed is a configuration from the IPv4-only era, and the default keeps it that way.

Changelog

One line each; the full entry is in CHANGELOG.md.

Added

  • A ticket that does not go stale: the Node ID plus exactly one relay URL and no IP addresses, so a client starts its handshake without waiting for an address lookup — and the lookup still runs, so the direct path and the hole punch are not given up.
  • Desktop: IPv6 candidates for hole punching, off by default.

Changed

  • Server and local proxy: nothing configured now means one fixed relay (pinned) rather than iroh's default of every N0 relay with a migrating home relay.
  • A Node ID and a ticket can be configured together, and both are used: the Node ID is the identity, the ticket's addresses are the paths.

Fixed

  • A ticket that names a different endpoint is refused instead of being silently resolved in favour of the configured Node ID.

Before upgrading

The server

  • One default changed, and it is worth knowing about. A configuration that names no relay mode now gets one fixed relay instead of every N0 relay with a home relay chosen by latency. That is deliberate: a relay that migrates drops the connections routed through it. Set relay_mode = "default" explicitly to get the old behaviour back, or relay_mode = "custom" with a relay of your own.
  • Nothing else has to be changed. No key is added, removed or renamed, and every key keeps its meaning. The protocol, the ALPN and the L4 preface are the same on the wire, so the clients of 1.1.1 keep working against this server.
  • Docker: pin :1.2.0 rather than :latest if you want the version to stay put.

The clients

  • Nothing to enroll, nothing to rescan. The handshake is unchanged on the wire, and a client that has no device key keeps using its secret.
  • The server prints a stable ticket now. It is the Node ID plus one relay URL; a client configured with it starts its handshake at once instead of waiting for an address lookup.
