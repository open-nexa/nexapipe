# NexaPipe 1.1.1 — the tunnel's runtime, and the credential it bought

A patch release, and a Windows one: the desktop app's service is given the
Wintun runtime it needs to create the tunnel, and a start that fails after
spending an enrollment token keeps the credential that token bought.

**Nothing has to be enrolled again.** The handshake, the ALPN and the L4 preface
are unchanged on the wire, so a 1.1.0 client talks to a 1.1.1 server and the
other way round.

> [!WARNING]
> **The macOS and Windows desktop bundles are published unsigned.**
>
> - `macos` — the `.dmg` and the `.app` inside it carry no Developer ID
>   signature and are not notarized. macOS Gatekeeper refuses them until the
>   user allows them by hand.
> - `windows` — the NSIS installer (`-setup.exe`) carries no Authenticode
>   signature. Windows SmartScreen refuses it until the user allows it by hand.
>
> A code signature costs money — the Apple Developer Program is $99 a year and a
> Windows certificate is bought per year on top of that — and this project has
> no revenue, so the desktop bundles ship without one. Everything else is signed:
> the Android APK carries the release keystore, the server archives carry a
> checksum, and the container image is signed with the release key and carries
> the provenance attestation.
>
> On macOS the refusal is the strict one: the app does not open until the user
> chooses "Open Anyway" in the dialog, which is a click in System Settings →
> Privacy & Security. On Windows it is the same shape. The Tauri updater's own
> signature is separate from the operating system's and is produced when the
> release build runs with its signing key, so an update installs the same way
> as the first install does whenever the release carried one.

## What's new

The full list is in
[CHANGELOG.md](https://github.com/open-nexa/nexapipe/blob/main/CHANGELOG.md);
these are the ones that change what a device does.

- **The Windows service is given the runtime it needs to create the tunnel.**
  The service binary is copied under `C:\Program Files\Nexa\Service` so that the
  control manager runs a file the ordinary user cannot replace — but only the
  binary was copied. The service creates the tunnel from its own directory, and
  the Wintun runtime was not there, so every service-mode TUN start failed with
  `wintun.dll not found` *after* the authentication had already succeeded, which
  reads like a backend problem. The install now resolves the runtime the app
  ships, copies it in beside the service binary and checks the copy the same way
  the binary's copy is checked; an install that cannot find it fails rather than
  registering a service whose tunnel can never come up. The uninstaller takes
  the runtime away again with the binary.

- **A start that fails keeps the credential its enrollment bought.** A
  registration token is spent by the first connection that presents it, and the
  credential the server answers with is the only copy left. The TUN device is
  created after that connection, so the most common failure was also the one
  that lost it: the instance holding the credential was dropped, both start
  paths unregistered the manager right after reporting the failure, and the
  frontend only read the credential on the success path. The credential is now
  moved out of the group before every failure return and every teardown, kept
  where the read command can still find it, and collected on the failure path
  as well as the successful one.

- **A local-proxy start that fails says so.** The mode was set before the listen
  socket existed, and the failure path did not put it back, so the status
  answered "running" with nothing listening — the frontend took the start as a
  success and the failure was never read and never shown.
## Before upgrading

### The server

**Nothing.** No configuration key is added, removed or renamed, and the protocol,
the ALPN and the L4 preface are the same on the wire. Docker: pin `:1.1.1`
rather than `:latest` if you want the version to stay put.

### The clients

- **Nothing to enroll, nothing to rescan.** The handshake is unchanged on the
  wire, and a client that has no device key keeps using its secret.

- **Windows: a service that is installed is registered again by the upgrade.**
  That is what puts the Wintun runtime beside the service binary, and it is the
  only step this release needs on that platform. A service the user had stopped
  stays stopped — the upgrade leaves it alone — and the Settings page can
  register it again when it is wanted. A service that was never installed needs
  nothing either; the first registration copies the runtime in from the start.

## Not in this release

Arbitrary destinations (the route table stays the only thing that decides where
a connection goes), an iOS client, key expiry and rotation, a relay of our own,
packaging for brew / winget / scoop, and a mesh. The reasons are in
[§0 of the roadmap](https://github.com/open-nexa/nexapipe/blob/main/docs/ROADMAP.md#0-the-v100-decision-2026-10-20).
