# NexaPipe 0.6.1 — configured

A release about the config surface: a fresh server starts with a usable config
and a stable identity, the endpoint's credentials no longer have to live inside
`config.toml`, and a `0644` bind mount starts instead of being refused. Two
configuration keys are added (`[iroh] secret_key_file` and
`relay_auth_token_file`) and none is removed or renamed, so a `config.toml`
written for 0.6.0 still loads.

## Added

- **First run writes a config and an identity.** Start the server with no
  `config.toml` and it writes a minimal one — `[auth] enabled = true`, no
  plaintext listener, no routes. Start with a config that has no
  `[iroh] secret_key` and the server generates one and writes it back, so the
  endpoint's Node ID survives a restart without running `--generate-secret` by
  hand. A key that does not parse refuses the start; a config that cannot be
  written still starts, on a throwaway identity, with a warning.

- **`[iroh]` credentials can live outside `config.toml`.** Two keys point at a
  separate `0600` file holding the value instead of spelling it inline:
  `secret_key_file` and `relay_auth_token_file` (relative paths read against
  the config's directory). Two environment variables carry the value directly:
  `NEXAPIPE_IROH_SECRET_KEY` and `NEXAPIPE_RELAY_AUTH_TOKEN`. Sources rank
  env → file → inline, and naming more than one source for one credential is
  refused at load.

- **A secrets-directory path that works with no `[iroh]` table.**
  `NEXAPIPE_IROH_SECRET_KEY_FILE` names the key file by absolute path. A
  missing env-named file is generated into on first start (`0600` on Unix),
  and the key is never written back into `config.toml`. The environment
  credentials apply even when the config has no `[iroh]` table at all — the
  docker first-run path. The compose setup now mounts `./secrets` at
  `/app/secrets` and wires the variable to `/app/secrets/iroh.key`; back that
  directory up together with `config/`.

## Changed

- **Config-file permissions are no longer checked at start or on reload.** The
  server used to refuse to start (and a reload could not turn 2FA on) when
  `config.toml` was group- or world-reachable and held a credential. That gate
  is gone — a `0644` bind mount starts, which is the ordinary Docker arrival
  mode. The trade-off is on the operator: any account that can read the file
  can copy every credential in it. `chmod 600` remains recommended, and the
  generated first-run file is still written `0600`. The credential sidecar
  files (`secret_key_file`, `relay_auth_token_file`,
  `NEXAPIPE_IROH_SECRET_KEY_FILE`, `config.toml.admin-token`) are still
  enforced `0600` on Unix and refuse the load otherwise.

- **The default `--config` path is Docker-friendly.** It is now
  `./config/config.toml` (was `./config.toml`), and `NEXAPIPE_CONFIG_DIR`
  shifts that default to `<dir>/config.toml`. `--config` always wins.

- **Docs: the invite QR code renders with correct line spacing on macOS.** The
  generated page used a line-height that collapsed the code block on Safari.

## Fixed

- **Android: the `tun-proxy` feature's stop path is gated on Android.**
  `nativeStopTunProxy` imported `ndk_context` and called an Android-only NDK
  function unconditionally, so a host build with `--features tun-proxy` failed
  to link. Both are now `#[cfg(target_os = "android")]`.

## Before upgrading

- Two configuration keys are added and none is removed or renamed: a
  `config.toml` that works on 0.6.0 still loads.
- The default `--config` path moves from `./config.toml` to
  `./config/config.toml`. If you launch the server with no `--config` flag,
  move your file into `config/` or pass `--config config.toml` explicitly.
  Docker users who set `NEXAPIPE_CONFIG_DIR=/app/config` need no change.
- **A permissive `config.toml` no longer refuses to start.** If you relied on
  the server refusing a world-readable config holding credentials, that check
  is gone — keep the file private (`chmod 600`) or move credentials to a
  sidecar file or the environment. Sidecar files are still checked.
- A config with no `[iroh] secret_key` gets one generated on first start and
  written back. If you relied on a fresh Node ID per restart, set
  `NEXAPIPE_NO_PERSIST_IDENTITY=1`.
- Naming more than one source for a credential is refused at load.
- Docker: pin `:0.6.1` rather than `:latest` if you want the version to stay
  put.

## Not in this release

The size-and-performance measurement work (a `size-report` CI job plus
criterion benchmarks) was planned for this number and moved to 0.6.2: the
config-surface improvements above were already on `main` and ready to ship. See
[the roadmap](https://github.com/open-nexa/nexapipe/blob/main/docs/ROADMAP.md)
for the updated ordering.
