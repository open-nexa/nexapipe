# NexaPipe 1.2.0 — a ticket that does not go stale

A minor release. It opens one new thing on the client — a ticket that does not
go stale — and it changes one default on the server: nothing configured now
means one fixed relay rather than every N0 relay with a home relay chosen by
latency, because a relay that migrates drops the connections routed through it.

**Nothing has to be enrolled again.** The handshake, the ALPN and the L4 preface
are unchanged on the wire, so a 1.1.1 client talks to a 1.2.0 server and the
other way round.

> [!WARNING]
> **The macOS and Windows desktop bundles are published unsigned.**
>
> - `macos` — the `.dmg` and the `.app` inside it carry no Developer ID
>   signature and are not notarized. macOS Gatekeeper refuses them until the
>   user allows them by hand.
> - `windows` — the NSIS installer (`-setup.exe`) carries no Authenticode
>   signature. Windows SmartScreen refuses it until the user allows it by hand.
>
> A code signature costs money — the Apple Developer Program is $99 a year and a
> Windows certificate is bought per year on top of that — and this project has
> no revenue, so the desktop bundles ship without one. Everything else is signed:
> the Android APK carries the release keystore, the server archives carry a
> checksum, and the container image is signed with the release key and carries
> the provenance attestation.
>
> On macOS the refusal is the strict one: the app does not open until the user
> chooses "Open Anyway" in the dialog, which is a click in System Settings →
> Privacy & Security. On Windows it is the same shape. The Tauri updater's own
> signature is separate from the operating system's and is produced when the
> release build runs with its signing key, so an update installs the same way
> as the first install does whenever the release carried one.

## What's new

The full list is in
[CHANGELOG.md](https://github.com/open-nexa/nexapipe/blob/main/CHANGELOG.md);
these are the ones that change what a device does.

- **A ticket that does not go stale.** An ordinary ticket carries an address,
  and an address carries two things with very different lifetimes: the **Node
  ID**, which is the endpoint's public key and changes only if the secret key
  changes, and the **addresses** — the relay URLs and the IP addresses — which
  change whenever the host moves, the socket gets a new port, or the home relay
  migrates. The addresses are what make an ordinary ticket go stale, and a
  stale ticket is worse than no ticket: it sends the client to an address that
  no longer answers. That is why deployments end up carrying a bare Node ID
  instead — and why a Node ID alone has to wait for an address lookup before the
  first packet can go anywhere.
  A **stable ticket** is the Node ID plus exactly one relay URL and no IP
  addresses at all. The Node ID keeps the identity fixed, which is the part an
  operator can actually pin, and the relay URL gives the client a path it can
  use immediately: iroh does not wait for an address lookup when it already
  knows any path, so a client holding this ticket starts its handshake at once
  instead of after a DNS and pkarr round trip — which, in a network where those
  lookups are slow or blocked, is the difference between a connection and a
  timeout. The lookup still runs, and its result is merged into the path set
  when it arrives: the direct addresses the peer publishes are still used and
  hole punching still happens. The ticket removes the *wait*, not the
  *possibility* of a direct path.
  The server prints one at start-up beside the ordinary ticket — "Stable ticket
  (does not go stale)" — and says so when the relay mode pins no relay, in which
  case the ticket is the Node ID alone.

- **Nothing configured means one fixed relay.** iroh's own default is every N0
  relay with the home relay chosen by latency, and it may migrate between them
  — and every migration drops the connections routed through it, a WebSocket in
  particular. The server and the CLI's `--local-proxy` were the two endpoints
  left migrating: the local proxy resolved "nothing configured" to no mode at
  all and handed the endpoint to iroh's default. Both resolve to `pinned` now,
  the same default the desktop app and the Android client already used — and a
  fixed relay is also what makes the stable ticket name a relay the endpoint
  stays registered at. A configuration that names a mode explicitly is
  unaffected: `default` still means every N0 relay, and `custom` still means
  the one relay the operator runs.

- **A Node ID and a ticket can be configured together, and both are used.** The
  Node ID is the identity and the ticket's addresses are the paths. Before, a
  configured Node ID won and the ticket was ignored entirely — so a ticket that
  carried the path was thrown away in favour of the bare Node ID, and the
  client was back to waiting for a lookup. A blank ticket field is no ticket at
  all: a template or an unset placeholder leaves `server_ticket = ""` around a
  node ID that was working before the field existed, and an empty string is not
  a ticket anybody issued. A ticket field holding a bare Node ID still works.

- **A ticket that names a different endpoint is refused.** The two names are
  compared now, and a disagreement is an error rather than something resolved in
  favour of either: a ticket for the wrong endpoint reaches the wrong endpoint,
  and no amount of address fixing repairs that.

- **The desktop can offer IPv6 candidates to hole punching, and does not by
  default.** The endpoint was bound IPv4-only, because on a host whose IPv6
  exists but cannot carry full-size QUIC datagrams (PPPoE: v6 MTU 1480, ICMPv6
  "packet too big" filtered) iroh's net report calls v6 usable and path
  migration moves traffic onto it — where every datagram above the real MTU
  fails, which reads as a connection that dies a few seconds in. The IPv4-only
  bind is still the default; the new `useIpv6` setting turns the IPv6 socket on,
  which puts IPv6 candidates in the set hole punching offers. That set is the
  one the server and the Android app already publish, so turning it on makes the
  desktop's direct path the same shape as theirs. It is off by default because
  a configuration written before the setting existed is a configuration from the
  IPv4-only era, and the default keeps it that way.

## Before upgrading

### The server

**One default changed, and it is worth knowing about.** A configuration that
names no relay mode now gets one fixed relay instead of every N0 relay with a
home relay chosen by latency. That is deliberate — a relay that migrates drops
the connections routed through it. Set `relay_mode = "default"` explicitly to
get the old behaviour back, or `relay_mode = "custom"` with a relay of your own.

**Nothing else has to be changed.** No configuration key is added, removed or
renamed, and every key keeps its meaning. The protocol, the ALPN and the L4
preface are the same on the wire, so the clients of 1.1.1 keep working against
this server. Docker: pin `:1.2.0` rather than `:latest` if you want the version
to stay put.

### The clients

- **Nothing to enroll, nothing to rescan.** The handshake is unchanged on the
  wire, and a client that has no device key keeps using its secret.

- **The server prints a stable ticket now.** It is the Node ID plus one relay
  URL; a client configured with it starts its handshake at once instead of
  waiting for an address lookup.

## Not in this release

Arbitrary destinations (the route table stays the only thing that decides where
a connection goes), an iOS client, key expiry and rotation, a relay of our own,
packaging for brew / winget / scoop, and a mesh. The reasons are in
[§0 of the roadmap](https://github.com/open-nexa/nexapipe/blob/main/docs/ROADMAP.md#0-the-v100-decision-2026-10-20).
