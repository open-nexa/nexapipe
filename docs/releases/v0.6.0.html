Release

NexaPipe 0.6.0

Identity finally goes as far as the device. One credential per device, issued at enrollment and revocable on its own, and every install answering as one named device of itself — so revoking a laptop no longer means re-enrolling a phone, and a device struck out loses the connections it is already holding instead of keeping them until it hangs up. Alongside it: request latency as a histogram, the write half of the management surface, and a desktop that shares its DNS with the other TUN apps on the machine.

10 October 2026 · one tag ships the server archives, the desktop bundles, the Android APK and the container image.

What's new

0.6.0 follows 0.5.0, released 7 October 2026. One configuration key is added and none is removed, so a config.toml that works on 0.5.0 loads unchanged — but two things behave differently without being configured to, and both are listed under before upgrading.

One credential per device, rather than one shared by every device

  • [auth.clients.<id>] gains a devices table: each entry carries a secret of its own, issued at enrollment and revocable on its own, so striking one out no longer rotates the rest — what used to make revoking a laptop mean re-enrolling a phone.
  • The credential is still a TOTP secret and the handshake still HMAC-SHA256 over nonce ‖ timestamp; what changed is which secret is looked up. A client carrying only secret keeps working exactly as it did — that is the path a peer naming no device takes, and the path every config written before this release is on.
  • A revoked device loses the connections it is already holding. Revocation used to rewrite config.toml and stop there: the device could not connect again, but it went on serving on everything it had open until it hung up — which is the one thing revocation is for. The reload that notices what left [auth] closes them now, at both levels: a client that left takes every device under it, a device that left takes only its own.
  • They go with a new close code, 6, which both clients turn into an error saying the credential is gone and that trying again is not going to help — the natural reading of a refused connection is a code typed wrong, and there is no code to retype.

Every install answers as one named device of itself

  • A device name is what makes the table above reachable from somewhere other than an operator's shell. The desktop answers after its hostname, Android after the device model, eight random characters behind either so two machines sharing a name do not collide into one entry nobody can revoke for one of them.
  • The name is claimed at enrollment and nowhere else, because the server picks the secret by what the response carries and refuses a device it has none filed for — a credential that answered as a name nobody asked for would be rejected rather than quietly accepted under the client's shared secret.
  • Existing credentials therefore carry on answering exactly as they do today, and nothing re-enrolls on its own. Both apps say what an unnamed device costs and offer the one thing that changes it, which is importing a registration invite again.

An access line says whose request it was

  • A connection carries the client and the device it authenticated as, so every access line ends with client=… device=… and /v1/connections answers who is connected rather than only how many.
  • A device that authenticated without naming itself is device=-; a request that never authenticated — 2FA off, or the plaintext HTTP listener, which runs no handshake — gets neither field, because a line answering "whose request was this" with a dash on all of them is noise rather than an answer.

nexapipe client list|add|revoke

  • The management surface has a write half. Each takes --device and writes config.toml through the same lock the server reads it with, and a running server picks the change up on its next reload.
  • /v1/* stays read-only on purpose: its token is one opaque value, with no scope and no rotation, which is not something to hand write access to in the same release as the identity model it would be changing.

Request latency as a histogram

  • nexapipe_request_duration_ms_bucket{le="…"}, beside _sum and _count, replaces nexapipe_request_duration_ms_total — which carried the same sum under a name a histogram cannot have. A p99 no longer takes arithmetic.
  • The boundaries are fixed at 1, 5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000 and 10000 milliseconds, plus +Inf. Anything that divided the old counter by nexapipe_requests_total for a mean can read _sum the same way.

Desktop

  • A page lists the connections a running proxy is holding, and the session carries its own totals beside them.
  • The TUN shares DNS and address space with the other TUN apps on the machine rather than taking both over, and a name outside the hijack is answered through the host's own resolver instead of being swallowed by the tunnel.
  • A running proxy says what quitting should do, rather than leaving the question unasked.
  • Seven smaller fixes: no empty window while the app starts; a launch whose window is never composited sends its start-up timings instead of none; the TUN resolver is the exclusive DNS route on Linux; a service an upgrade left behind is put back; a macOS service that was stopped stays stopped; the connecting indicator breathes with Reduce Motion on; and the webview is granted the permission it needs to read the service version.

Operations

  • Both READMEs carry a systemd unit for the server, beside the Docker section. It keeps a named account rather than DynamicUser=yes, because this server writes back into its own config — the 2FA counters, an enrolled device — and writes its admin token beside it.
  • docs/self-hosted-relay.md gains the same for the relay.
  • The root workspace is tested on Windows in CI, not only compiled. The job was windows-check; it is windows-test now and runs the same command the Linux and macOS runners do, so a bug that only appears when the tests execute no longer reaches a tag before CI sees one.

Also in this release

  • Dependencies: one batched upgrade across the workspace.

Changelog

Added

  • Server: one credential per device — a devices table under [auth.clients.<id>], each entry issued at enrollment and revocable on its own.
  • Client, desktop and Android: every install answers as one named device of itself, the desktop after its hostname and Android after the device model.
  • Server: an access line and /v1/connections say which client and which device a connection belongs to.
  • Server: nexapipe client list|add|revoke, each with --device.
  • Docs: a systemd unit for the server in both READMEs, and one for the relay in docs/self-hosted-relay.md.
  • Desktop: session totals, and a page that lists the connections a running proxy is holding.
  • Desktop: a running proxy says what quitting should do.
  • CI: the root workspace is tested on Windows, not only compiled.

Changed

  • Server: /metrics reports request latency as a histogram (nexapipe_request_duration_ms_bucket, _sum, _count) rather than as the counter nexapipe_request_duration_ms_total, which no longer exists.
  • Desktop: the TUN shares DNS and address space with the other TUN apps on the machine.
  • Dependencies: one batched upgrade across the workspace.

Fixed

  • Server: a device struck out kept the connections it already held. It could not connect again, but it went on serving on everything it had open until it hung up — which is the one thing revocation is for. Those connections are closed now, with close code 6.
  • Desktop: a name outside the hijack is answered through the host's own resolver, instead of the TUN swallowing it.
  • Desktop: an empty window is no longer shown while the app starts.
  • Desktop (Linux): the TUN resolver is the exclusive DNS route.
  • Desktop: the service is put back on the app's build when an upgrade leaves it behind.
  • Desktop (macOS): a service that was stopped stays stopped.
  • Desktop: the connecting indicator breathes with Reduce Motion on, rather than being exempt from the setting.
  • Desktop: the webview is granted the permission it needs to read the service version.
  • Desktop: the window is shown before the first frame is waited for.
  • Desktop: a launch that produced no frame sent no start-up timings at all. The wait after show() had no end, so a window the compositor never drew — a minimized one, or one on a machine that went to sleep — never reached the finally that sends the timings either. The wait is bounded at two seconds now and reports whether a frame came, so such a launch is logged as one that produced none rather than as one that never happened.
  • A peer listing takes one reading of the clock for the whole list rather than one per entry, so two peers are no longer ordered by when the loop happened to reach them.
  • Desktop (macOS): the bundle carries the content security policy the other two platforms use. Platform configs merge as JSON Merge Patch, in which null means remove the key — so app.security.csp = null deleted the policy rather than relaxing it, and the macOS app ran with none while Windows and Linux kept the baseline. The webview holds every app command permission either way.
  • [peers] refuses a key it does not recognise. allow is the section's only key and an absent one means unrestricted, so allowd = [...] was dropped by serde and left a server that looked restricted and was not, with nothing in the log to say so.
  • Android: switching the VPN off no longer risks a native crash. nativeStopTunProxy was the one JNI entry point with no barrier against unwinding, and a panic there leaves an extern "system" frame — on Android a native crash rather than a Java exception.
  • --qr-out writes the file private from the moment it exists, and will not write over one. The file carries the TOTP secret in the clear; it used to be created by fs::write and made private afterwards, so in between it was readable by anyone with access to the machine, and fs::write truncates whatever is at the path and follows a symlink to reach it. A path that already exists is now refused instead of overwritten.

Before upgrading

  • One configuration key is added and none is removed or renamed: a config.toml that works on 0.5.0 loads unchanged on 0.6.0, and a client written before devices existed answers exactly as it did.
  • /metrics loses nexapipe_request_duration_ms_total and gains the histogram. A scrape looking for the old counter will not find it: read nexapipe_request_duration_ms_sum instead, and divide by nexapipe_requests_total for the same mean.
  • Revoking a device now closes the connections it already holds. Anything that treated a revocation as "no new connections, but the old ones finish" — a drain script, a test — sees them end immediately instead.
  • Both clients turn close code 6 into "the credential is gone"; an older client library reads it as an unknown code. Mixing versions across a revocation is safe, just less explanatory.
  • A device enrolled before it could name itself keeps answering as nobody, and is still filed under the client's shared secret. Importing a registration invite again is what makes it a named device — nothing re-enrolls on its own.
  • Docker: pin :0.6.0 rather than :latest if you want the version to stay put.
