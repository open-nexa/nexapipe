Release

NexaPipe 1.0.0

The first release that changes what a client is allowed to reach and where the server keeps what it learns. A device's credential can be a key instead of a shared secret, a client can be held to the ports it may reach and not only to the names, the server's runtime state lives in a file of its own, and both clients can bring the tunnel back by themselves. No client has to be enrolled again — the handshake, the ALPN and the L4 preface are unchanged on the wire, so a 0.6.1 client talks to a 1.0.0 server and the other way round. What did change is what a deployment and a device have to do.

24 October 2026 · one tag ships the server archives, the desktop bundles, the Android APK and the container image.

Container image

Published with everything else, as one multi-arch manifest for linux/amd64 and linux/arm64. Both READMEs carry a systemd unit for the server now as well.

# This release exactly
docker pull ghcr.io/open-nexa/nexapipe:1.0.0

# The newest stable release (:latest never points at a pre-release)
docker pull ghcr.io/open-nexa/nexapipe:latest

docker-compose.yaml names the published image, so docker compose up pulls it rather than building — --build still builds locally under the same name.

The image runs as uid 1000, not root. The three mounted directories have to be writable by that uid, so run sudo chown -R 1000:1000 config secrets logs before the first start of an upgraded deployment. Without it the iroh.key cannot be opened and is regenerated — a new Node ID, and every client stops finding the server. See before upgrading.

What's new

1.0.0 follows 0.6.1. No configuration key is removed or renamed and every key this cycle adds is optional, so a config.toml that works on 0.6.1 still loads — but five things behave differently without being configured to, and all of them are listed under before upgrading.

A device can hold a key instead of a shared secret

  • A device that runs unattended has nobody to read a code to it, so it signs each challenge with an Ed25519 key the server holds the public half of. The private half never leaves the device, and there is no code for anyone to read.
  • Issued with nexapipe client add <ID> --device <NAME> --public-key <HEX>. A device that has no key keeps using its secret, and the two are checked the same way.

A client can be held to the ports it may reach

  • allow_hosts grew a port dimension: allow_ports names the ports a client may reach, and allow_ports_strict says whether that list is checked against the port the request is served from or the one the client names.
  • Leaving allow_ports out leaves a client with every port it had.

The server's state lives in a file of its own

  • The lockout counters and the TOTP step memories no longer live in config.toml, so the configuration is not rewritten for them and a host edit cannot lose a counter.
  • The state file is named after the configuration — config.toml puts its state in config.state.toml — and the old state.toml beside it is still read when the new one is not there yet.

The third-party boundary is two settings now

  • relay_mode = "custom" really excludes n0's relays, and [iroh] discovery = "none" switches the address lookup off — a Node ID is then not enough to reach the endpoint, and a peer has to bring an address of its own.
  • Leaving [iroh] discovery out keeps n0's address lookup, which is what a config written before the key existed does.

Both clients can stay up on their own

  • The desktop starts with the system and hides in the tray; Android comes back after a reboot. Both are off until the user asks for them.
  • The Android client no longer hard-codes 10.0.1.0/24 — a great many home routers use it, and the tunnel swallowed the router's own addresses there. It picks the first block the host will take.
  • The server and the client used to disagree about what *.example.com means, and a name the client decided to tunnel could be a name the server had no route for. There is one rule now, on both sides.

A backend can be reached over TLS, retried, and taken out of rotation

  • https:// backends and HTTP/2, [retry] and [circuit_breaker] — the hop can be encrypted, tried again, and dropped when it stays down.
  • Leaving them out keeps one try, the machine's own trust store, and the defaults the section already had.

Changelog

One line each; the full entry is in CHANGELOG.md.

Added

  • Server: a device can hold an Ed25519 key instead of a shared secret, issued with client add --device --public-key, so a device that runs unattended needs no code.
  • Server: allow_ports and allow_ports_strict hold a client to the ports it may reach and not only to the names.
  • Server: [limits], [backends] ca_file, [retry], [circuit_breaker], [iroh] discovery and the six [timeouts] phase keys — all optional, and each one leaves the old behaviour in place when it is left out.
  • Server: https:// backends and HTTP/2, so the hop to a backend can be encrypted.
  • Clients: a device key, a latency probe that reaches the UI, and the ability to stay up without being opened by hand.

Changed

  • Server: the runtime state moves out of config.toml into a file of its own beside it, so the configuration is not rewritten for the counters.
  • Server: the container image runs as uid 1000 rather than root.
  • Server: the protocol is chosen at the handshake instead of by the first byte of each stream, so a client that speaks HTTP and L4 holds a connection for each.
  • Clients: the tunnel's address block is picked rather than hard-coded, and the server and the client spell a host pattern the same way.
  • Desktop: the credentials move out of localStorage into an encrypted store whose master key the OS keychain holds.

Fixed

  • Server: a 2FA code from a step that has already gone by is refused, and a refusal is not counted as a guess.
  • Server: a client's own identity is checked before its connections are counted, so a revoked client loses the connections it already held.
  • Client: the tunnel descriptor is closed exactly once, and every JNI entry point catches a panic before it leaves the frame.

Before upgrading

The server

  • Docker: the image no longer runs as root. It runs as uid 1000, so the three mounted directories have to be writable by that uid. Run sudo chown -R 1000:1000 config secrets logs before the first start, and with sudo — the files the old root image wrote are root-owned. Skipping it does not always fail loudly: an iroh.key that cannot be opened is regenerated, which is a new Node ID, and every client that stored the old one stops finding the server.
  • A config key the file does not know now refuses the start. In 0.6.1 only [peers] and [auth] refused unknown keys and the rest dropped them silently; every section refuses them now, the top level included. Run the server once against your config and fix what it names — a stray key at the top of the file is refused the same way: 
    unknown field `stray_key`, expected one of `default_backend`, `debug`, `routes`, `server`, `iroh`, ...
This build does not know that key: remove it, or fix its spelling.
    One key is worth naming in advance, because a config can carry it today: [admin] token is not a key. The admin token is generated into <config>.admin-token and that file is the only source of it, so a config that names a token is refused rather than parsed and dropped — the operator finds out that the token they set is not the token in use, instead of finding out when the management surface answers 401.
  • The runtime state moves into a file of its own. The counters and the TOTP step memories are written to a file named after the configuration — config.toml puts its state in config.state.toml. The old state.toml beside it is still read when the new one is not there yet, and the counters are still read from config.toml, so existing lockouts survive. The configuration directory has to stay writable.
  • Removed keys are still accepted and logged as ignored: [server] tls_enabled, tls_listen_addr, cert_path and key_path, the route-level cert_path, key_path and redirect_to_https, and the [acme] section. TLS is terminated by the backend now.
  • Nothing else changed: no configuration key is removed or renamed, every key added in this cycle is optional, [auth] enabled still defaults to false for a config with no [auth] section, and the config file's own permissions are still not gated. The CLI is unchanged apart from client add --public-key.
  • Docker: pin :1.0.0 rather than :latest if you want the version to stay put.

The clients

  • Nothing to enroll, nothing to rescan. An existing secret keeps working: the handshake is the same on the wire, and a client that has no key keeps using its secret.
  • Android: the tunnel's address block changes. It was 10.0.1.0/24 and is now the first block the host will take out of 198.18.0.0/24, 198.19.0.0/24, 100.100.0.0/24, 172.26.0.0/24, 10.200.0.0/24 and 10.0.0.0/24. The addresses are internal to the tunnel; a rule of your own that hard-codes 10.0.1.x needs updating.
  • Desktop: the credentials move out of localStorage. They go into an encrypted file whose master key the OS keychain holds. The migration is automatic — a payload written before it is read once and its secrets are written into the encrypted store. Nothing to do by hand.
  • New, and off until asked for: starting with the system, coming back after a reboot, and a device key instead of a secret.
