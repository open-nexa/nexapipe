# NexaPipe 1.0.0 — the third-party boundary, closed

The first release that changes what a client is allowed to reach and where the
server keeps what it learns. A device's credential can be a key instead of a
shared secret, a client can be held to the ports it may reach and not only to
the names, the server's runtime state lives in a file of its own, and both
clients can bring the tunnel back by themselves.

**No client has to be enrolled again.** The handshake, the ALPN and the L4
preface are unchanged on the wire, so a 0.6.1 client talks to a 1.0.0 server
and the other way round. What did change is what a deployment and a device have
to do — see [before upgrading](#before-upgrading).

## What's new

The full list is in
[CHANGELOG.md](https://github.com/open-nexa/nexapipe/blob/main/CHANGELOG.md);
these are the ones that change what a deployment or a device does.

- **A device can hold a key instead of a shared secret.** A device that runs
  unattended signs each challenge with an Ed25519 key instead of answering with
  a code, so there is nothing for anyone to read. Issued with
  `nexapipe client add <ID> --device <NAME> --public-key <HEX>`.

- **A client can be held to the ports it may reach.** `allow_hosts` grew a port
  dimension: `allow_ports` names the ports, and `allow_ports_strict` says
  whether the list is checked against the port the request is served from or
  the one the client names.

- **The third-party boundary is two settings now.** `relay_mode = "custom"`
  really excludes n0's relays, and `[iroh] discovery = "none"` switches the
  address lookup off — a Node ID is then not enough to reach the endpoint.

- **Both clients can stay up on their own.** The desktop starts with the
  system and hides in the tray; Android comes back after a reboot. Both are off
  until the user asks for them.

- **Both clients pick their address block, and both sides spell a name the
  same way.** The Android client no longer hard-codes `10.0.1.0/24`, which a
  great many home routers use; and the server and the client used to disagree
  about what `*.example.com` means.

- **A backend can be reached over TLS, retried, and taken out of rotation.**
  `https://` backends, HTTP/2, `[retry]` and `[circuit_breaker]`.

- **The protocol is chosen at the handshake.** Each protocol gets a connection
  of its own rather than being told apart by the first byte of each stream, so
  a client that speaks both pays for one more handshake.

## Before upgrading

### The server

**1. Docker: the image no longer runs as root.** It runs as uid 1000, so the
three mounted directories have to be writable by that uid:

```bash
sudo chown -R 1000:1000 config secrets logs
```

Run it **before the first start**, and with `sudo` — the files the old root
image wrote are root-owned. Skipping it does not always fail loudly: an
`iroh.key` that cannot be opened is *regenerated*, which is a new Node ID, and
every client that stored the old one stops finding the server.

**2. A config key the file does not know now refuses the start.** In 0.6.1
only `[peers]` and `[auth]` refused unknown keys and the rest dropped them
silently. Every section refuses them now, the top level included — a stray key
at the top of the file is refused the same way as a typo inside a section. A
key that is not read is a key the operator believes is read, so it is named
rather than ignored:

```
unknown field `stray_key`, expected one of `default_backend`, `debug`, `routes`, `server`, `iroh`, ...
This build does not know that key: remove it, or fix its spelling.
```

Run the server once against your config and fix what it names. One key is worth
naming in advance, because a config can carry it today: **`[admin] token` is
not a key.** The admin token is generated into `<config>.admin-token` and that
file is the only source of it, so a config that names a token is refused rather
than parsed and dropped — the operator finds out that the token they set is not
the token in use, instead of finding out when the management surface answers
401.

**3. The runtime state moves into a file of its own.** The counters
(`failed_attempts`, `locked_until`, `last_used`) and the TOTP step memories
are written to a file named after the configuration — `config.toml` puts its
state in `config.state.toml`, `config.prod.toml` in `config.prod.state.toml`.
The old `state.toml` beside the configuration is still read when the new one
is not there yet, and the counters are still read from `config.toml`, so
**existing lockouts survive the upgrade**. The configuration directory has to
stay writable.

**4. Removed keys are still accepted.** `[server] tls_enabled`,
`tls_listen_addr`, `cert_path` and `key_path`, the route-level `cert_path`,
`key_path` and `redirect_to_https`, and the `[acme]` section are logged as
ignored and can be deleted. TLS is terminated by the backend now.

**5. What did not change.** No configuration key is removed or renamed, and
every key added in this cycle is optional. `[auth] enabled` still defaults to
`false` for a config that has no `[auth]` section, so an existing deployment
does not suddenly demand a credential its clients were never given — only the
*shipped example* now starts with 2FA on and no client enrolled. The config
file's own permissions are still not gated. The CLI is unchanged apart from
`client add --public-key`.

### The clients

- **Nothing to enroll, nothing to rescan.** An existing secret keeps working:
  the handshake is the same on the wire, and a client that has no key keeps
  using its secret.

- **Android: the tunnel's address block changes.** It was `10.0.1.0/24` and is
  now the first block the host will take out of `198.18.0.0/24`,
  `198.19.0.0/24`, `100.100.0.0/24`, `172.26.0.0/24`, `10.200.0.0/24` and
  `10.0.0.0/24`. The addresses are internal to the tunnel; a rule of your own
  that hard-codes `10.0.1.x` needs updating.

- **Desktop: the credentials move out of `localStorage`.** They go into an
  encrypted file whose master key the OS keychain holds. The migration is
  automatic — a payload written before it is read once and its secrets are
  written into the encrypted store. Nothing to do by hand.

- **Desktop: the service is replaced during the upgrade.** It runs a copy of
  the app's own binary from a root-owned directory, and an upgrade used to
  leave the service running the build it was started with — launchd and systemd
  read a job definition once, and the path the service runs from does not
  change. So the app was new and the service was old, the two did not speak the
  same protocol, and the panel showed a service that was *running* with every
  button greyed out. The upgrade now puts the new binary in place: a service
  you had stopped stays stopped, the account it serves is unchanged, and if it
  cannot be done the installer puts the machine back the way it found it and
  exits with a non-zero code rather than reporting success over a half-upgraded
  machine. A service left behind by an upgrade is reported as drift now, with
  the install button offered for it.

- **New, and off until asked for:** starting with the system, coming back
  after a reboot, and a device key instead of a secret.

## Not in this release

Arbitrary destinations (the route table stays the only thing that decides
where a connection goes), an iOS client, key expiry and rotation, a relay of
our own, packaging for brew / winget / scoop, and a mesh. The reasons are in
[§0 of the roadmap](https://github.com/open-nexa/nexapipe/blob/main/docs/ROADMAP.md#0-the-v100-decision-2026-10-20).
