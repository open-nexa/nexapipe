# NexaPipe 1.1.0 — the seams, and a cheaper path

A release that opens no new capability on the server and makes three of the things
around it replaceable. Which credential is checked is a seam a deployment can fill
with its own authenticator, the access log is a record rather than a line, and where
the proxy keeps what it keeps is a store with the file behind it.

**Nothing has to be enrolled again.** The handshake, the ALPN and the L4 preface are
unchanged on the wire, so a 1.0.0 client talks to a 1.1.0 server and the other way
round.

> [!WARNING]
> **The macOS and Windows desktop bundles are published unsigned.**
>
> - `macos` — the `.dmg` and the `.app` inside it carry no Developer ID
>   signature and are not notarized. macOS Gatekeeper refuses them until the
>   user allows them by hand.
> - `windows` — the NSIS installer (`-setup.exe`) carries no Authenticode
>   signature. Windows SmartScreen refuses it until the user allows it by hand.
>
> A code signature costs money — the Apple Developer Program is $99 a year and a
> Windows certificate is bought per year on top of that — and this project has
> no revenue, so the desktop bundles ship without one. Everything else is signed:
> the Android APK carries the release keystore, the server archives carry a
> checksum, and the container image is signed with the release key and carries
> the provenance attestation.
>
> On macOS the refusal is the strict one: the app does not open until the user
> chooses "Open Anyway" in the dialog, which is a click in System Settings →
> Privacy & Security. On Windows it is the same shape. The Tauri updater's own
> signature is separate from the operating system's and is present either way,
> so an update installs the same way as the first install does.

## What's new

The full list is in
[CHANGELOG.md](https://github.com/open-nexa/nexapipe/blob/main/CHANGELOG.md);
these are the ones that change what a deployment or a device does.

- **Which credential is checked is now a seam.** Which credentials exist is the
  core's business — a shared secret, a TOTP seed, an Ed25519 key — but *what
  checks them* is a decision, and a deployment that keeps its credentials in an
  identity provider rather than in `config.toml` had no way to say so.
  `Authenticator` is that decision written down as a trait. The built-in
  implementation reads the client table in the configuration, and the logic
  moved into it unchanged.

- **The access log is a record as well as a line.** The line is a fixed set of
  columns, written to a file and read by a script that splits it on spaces —
  the right shape for a log, and the wrong one for an audit trail.
  `AccessRecord` is those facts as values and `AccessSink` is what takes one: a
  deployment registers its own, and the core neither knows nor cares where the
  records end up.

- **Where the proxy keeps what it keeps is a store.** The configuration, the
  runtime counters and the admin token were three files at three paths, read
  and written by name. `Storage` says what a store has to do and a backend says
  how it does it. `FileStorage` is the backend that exists today, and it
  behaves exactly as the code behaved before.

- **A client can carry a ticket instead of a Node ID.** `[iroh] discovery =
  "none"` took the address lookup off the server; what was missing was
  everything a *client* needs to connect without it, because a Node ID nobody
  resolves is a name and not an address. A ticket carries the addresses, so it
  works with the lookup off.

- **Opening a tunnel is measured in the three phases it is made of.** A slow
  tunnel used to be one number, which cannot say whether the time went into
  this process or onto the network. The server publishes
  `nexapipe_l4_open_duration_ms`, `nexapipe_l4_route_duration_ms` and
  `nexapipe_l4_backend_duration_ms`, and the client logs the same split from
  its own side.

- **The path a phone's traffic takes got cheaper.** A packet on the desktop's
  TUN costs one allocation rather than an allocation and a copy; the TCP window
  is a credit that grows as the flow carries bytes rather than an allocation
  taken up front; the UDP flow table holds a hundred and twenty-eight flows
  instead of thirty-two; the application's first bytes no longer wait for the
  server's answer; the inner MTU is pinned to 1280; and a flow socket no longer
  waits to answer a small message.

- **The desktop app is 32% smaller.** `ui-desktop/src-tauri` is its own cargo
  workspace, so the tuning at the root applied to the server crates and to the
  Android library and to nothing on the desktop. It has a release profile now:
  the app goes from 39.1 MiB to 26.5 MiB, and the service binary it runs from
  19.0 MiB to 12.0 MiB. The cost is build time, and it is measured too — two
  minutes became three and a half.

- **The three crates are on crates.io.** `nexapipe`, `nexapipe-client` and
  `nexapipe-proto` carry what crates.io asks for, so an application that is
  not written in Rust can link the client.

## Before upgrading

### The server

**1. Nothing in the configuration has to change.** No key is removed or renamed,
no key is added, and every key keeps its meaning. A `config.toml` that works on
1.0.0 works here unchanged.

**2. The store is chosen by the command line or the environment, never by the
configuration.** `--storage` wins over `NEXAPIPE_STORAGE`, and the file backend
— the only one this build carries — reads and writes the same files as before.
A build without the `storage-sqlite` or `storage-postgres` feature says so
rather than pretending to open a database it has no driver for.

**3. What did not change.** The protocol, the ALPN and the L4 preface are the
same on the wire, so the clients of 1.0.0 keep working against this server.
Docker: pin `:1.1.0` rather than `:latest` if you want the version to stay put.

### The clients

- **Nothing to enroll, nothing to rescan.** The handshake is unchanged on the
  wire, and a client that has no device key keeps using its secret.

- **Android: the tunnel's inner MTU is 1280 now.** It was 1400, which can sit
  above the path's own MTU — the tunnel path is probed by PLPMTUD and observed
  to swing between roughly 1326 and 1452. A rule of your own that hard-codes the
  old number needs updating; the addresses themselves are unchanged.

- **Desktop: a discovery setting sits next to the relay mode.** It is off by
  default, and leaving it alone keeps n0's address lookup, which is what a
  client that has never heard of a ticket expects.

- **Desktop: the app and the service are both smaller.** Nothing to do: the
  release profile is the build's business, not the operator's.

## Not in this release

Arbitrary destinations (the route table stays the only thing that decides where
a connection goes), an iOS client, key expiry and rotation, a relay of our own,
packaging for brew / winget / scoop, and a mesh. The reasons are in
[§0 of the roadmap](https://github.com/open-nexa/nexapipe/blob/main/docs/ROADMAP.md#0-the-v100-decision-2026-10-20).
