Release

NexaPipe 1.1.1

A patch release, and a Windows one. The desktop app's service is given the Wintun runtime it needs to create the tunnel — only the service binary was copied under Program Files, so every service-mode TUN start failed with wintun.dll not found after the authentication had already succeeded — and a start that fails after spending an enrollment token keeps the credential that token bought, which was the only copy left. Nothing has to be enrolled again — the handshake, the ALPN and the L4 preface are unchanged on the wire, so a 1.1.0 client talks to a 1.1.1 server and the other way round.

5 November 2026 · one tag ships the server archives, the desktop bundles, the Android APK and the container image.

Downloads

Client app first, then the server. Nothing needs an account, and nothing is gated.

The macOS and Windows desktop bundles are published unsigned.
  • macos — the .dmg and the .app inside it carry no Developer ID signature and are not notarized. macOS Gatekeeper refuses them until the user allows them by hand.
  • windows — the NSIS installer (-setup.exe) carries no Authenticode signature. Windows SmartScreen refuses it until the user allows it by hand.

A code signature costs money — the Apple Developer Program is $99 a year and a Windows certificate is bought per year on top of that — and this project has no revenue, so the desktop bundles ship without one. Everything else is signed: the Android APK carries the release keystore, the server archives carry a checksum, and the container image is signed with the release key and carries a provenance attestation.

On macOS the refusal is the strict one: the app does not open until the user chooses “Open Anyway” in the dialog, which is a click in System Settings → Privacy & Security. The Tauri updater’s own signature is separate from the operating system’s and is produced when the release build runs with its signing key, so an update installs the same way as the first install does whenever the release carried one.

Container image

Published with everything else, as one multi-arch manifest for linux/amd64 and linux/arm64. Both READMEs carry a systemd unit for the server now as well.

# This release exactly
docker pull ghcr.io/open-nexa/nexapipe:1.1.1

# The newest stable release (:latest never points at a pre-release)
docker pull ghcr.io/open-nexa/nexapipe:latest

docker-compose.yaml names the published image, so docker compose up pulls it rather than building — --build still builds locally under the same name.

The image runs as uid 1000, not root. The three mounted directories have to be writable by that uid, so run sudo chown -R 1000:1000 config secrets logs before the first start of an upgraded deployment. Without it the iroh.key cannot be opened and is regenerated — a new Node ID, and every client stops finding the server. See before upgrading.

What's new

1.1.1 follows 1.1.0. It is a patch release, and a Windows one: three defects in the desktop app's service and start path, the first two of them shipped in v1.0.0. No configuration key is added, removed or renamed, and nothing on the wire changes — the handshake, the ALPN and the L4 preface are the same, so a 1.1.0 client talks to a 1.1.1 server and the other way round, and nothing has to be enrolled again.

The Windows service is given the runtime it needs to create the tunnel

  • The service binary is copied under C:\Program Files\Nexa\Service so that the control manager runs a file the ordinary user cannot replace — but only the binary was copied, and the service creates the tunnel from its own directory.
  • Every service-mode TUN start failed with wintun.dll not found, after the authentication had already succeeded, which reads like a backend problem rather than a missing runtime.
  • The install now resolves the runtime the app ships, copies it in beside the service binary and checks the copy the same way the binary's copy is checked. An install that cannot find the runtime fails rather than registering a service whose tunnel can never come up.
  • The uninstaller takes the runtime away again with the binary — the NSIS uninstaller included, which deleted the service binary and then removed the directory, and could not remove a directory the runtime was still in.

A start that fails keeps the credential its enrollment bought

  • A registration token is spent by the first connection that presents it, and the credential the server answers with is the only copy left. The TUN device is created after that connection, so the most common failure was also the one that lost it.
  • The instance holding the credential was dropped, both start paths unregistered the manager right after reporting the failure, and the frontend only read the credential on the success path. The device was left holding a spent token, and every later start was refused as unauthenticated.
  • The credential is now moved out of the group before every failure return and every teardown, kept where the read command can still find it, and collected on the failure path as well as the successful one.

A local-proxy start that fails says so

  • The mode was set before the listen socket existed and the failure path did not put it back, so the status answered “running” with nothing listening: the frontend took the start as a success and the failure was never read and never shown.

Changelog

One line each; the full entry is in CHANGELOG.md.

Fixed

  • Desktop: the Windows service is given the Wintun runtime it needs to create the tunnel — copied in beside the service binary, checked like it, and taken away again with it.
  • Desktop: a start that fails after spending an enrollment token keeps the credential that token bought, and the frontend collects it on the failure path as well as the successful one.
  • Desktop: a local-proxy start that fails reports itself as failed rather than running.

Before upgrading

The server

  • Nothing has to be changed in the configuration. No key is added, removed or renamed, and every key keeps its meaning. A config.toml that works on 1.1.0 works here unchanged.
  • Nothing else changed. The protocol, the ALPN and the L4 preface are the same on the wire, so the clients of 1.1.0 keep working against this server.
  • Docker: pin :1.1.1 rather than :latest if you want the version to stay put.

The clients

  • Nothing to enroll, nothing to rescan. The handshake is unchanged on the wire, and a client that has no device key keeps using its secret.
  • Windows: an installed service is registered again by the upgrade. That is what puts the Wintun runtime beside the service binary, and it is the only step this release needs on that platform. A service the user had stopped stays stopped — the upgrade leaves it alone — and the Settings page can register it again when it is wanted.
