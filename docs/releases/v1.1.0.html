Release

NexaPipe 1.1.0

A release that opens no new capability on the server and makes three of the things around it replaceable. Which credential is checked is a seam a deployment can fill with its own authenticator, the access log is a record rather than a line, and where the proxy keeps what it keeps is a store with the file behind it. The tunnel answers the way the protocol says it should, the path a phone's traffic takes is measured rather than assumed, and the desktop app is a third of its old size. Nothing has to be enrolled again — the handshake, the ALPN and the L4 preface are unchanged on the wire, so a 1.0.0 client talks to a 1.1.0 server and the other way round.

4 November 2026 · one tag ships the server archives, the desktop bundles, the Android APK and the container image.

Downloads

Client app first, then the server. Nothing needs an account, and nothing is gated.

The macOS and Windows desktop bundles are published unsigned.
  • macos — the .dmg and the .app inside it carry no Developer ID signature and are not notarized. macOS Gatekeeper refuses them until the user allows them by hand.
  • windows — the NSIS installer (-setup.exe) carries no Authenticode signature. Windows SmartScreen refuses it until the user allows it by hand.

A code signature costs money — the Apple Developer Program is $99 a year and a Windows certificate is bought per year on top of that — and this project has no revenue, so the desktop bundles ship without one. Everything else is signed: the Android APK carries the release keystore, the server archives carry a checksum, and the container image is signed with the release key and carries a provenance attestation.

On macOS the refusal is the strict one: the app does not open until the user chooses “Open Anyway” in the dialog, which is a click in System Settings → Privacy & Security. The Tauri updater’s own signature is separate from the operating system’s and is produced when the release build runs with its signing key, so an update installs the same way as the first install does whenever the release carried one.

Container image

Published with everything else, as one multi-arch manifest for linux/amd64 and linux/arm64. Both READMEs carry a systemd unit for the server now as well.

# This release exactly
docker pull ghcr.io/open-nexa/nexapipe:1.1.0

# The newest stable release (:latest never points at a pre-release)
docker pull ghcr.io/open-nexa/nexapipe:latest

docker-compose.yaml names the published image, so docker compose up pulls it rather than building — --build still builds locally under the same name.

The image runs as uid 1000, not root. The three mounted directories have to be writable by that uid, so run sudo chown -R 1000:1000 config secrets logs before the first start of an upgraded deployment. Without it the iroh.key cannot be opened and is regenerated — a new Node ID, and every client stops finding the server. See before upgrading.

What's new

1.1.0 follows 1.0.0. No configuration key is removed or renamed, and this cycle adds none: the client-side half of the discovery switch reuses the key the server already had. A config.toml that works on 1.0.0 still loads — but three things behave differently without being configured to, and all of them are listed under before upgrading.

Which credential is checked is now a seam

  • Which credentials exist is the core's business — a shared secret, a TOTP seed, an Ed25519 key — but what checks them is a decision. Authenticator is that decision written down as a trait, and a deployment that keeps its credentials in an identity provider rather than in config.toml can now say so.
  • The built-in implementation reads the client table in the configuration, and the logic moved into it unchanged: the same lock, the same order, the same refusals, the same counters.
  • The trait is called without the auth lock held, so an implementation that has to reach an identity provider does that reach before it takes the lock.

The access log is a record as well as a line

  • The line is a fixed set of columns, written to a file and read by a script that splits it on spaces — the right shape for a log and the wrong one for an audit trail.
  • AccessRecord is those facts as values and AccessSink is what takes one: a deployment registers its own, and the core neither knows nor cares where the records end up. A sink runs on a thread of its own, so one that reaches the network cannot hold up the log file.

Where the proxy keeps what it keeps is a store

  • The configuration, the runtime counters and the admin token were three files at three paths, read and written by name. Storage says what a store has to do — read the configuration, write a client's credential, count a lockout, hand out the admin token — and a backend says how.
  • FileStorage is the backend that exists today, and it behaves exactly as the code behaved before: the same files, the same locks, the same messages. The database backends arrive behind the storage-sqlite and storage-postgres features, and a build without them says so rather than pretending to open a database it has no driver for.
  • The store is chosen by --storage or by NEXAPIPE_STORAGE, and never by the configuration: a document cannot say where it lives, because it is read from there in the first place.

A client can carry a ticket instead of a Node ID

  • [iroh] discovery = "none" took the address lookup off the server; what was missing was everything a client needs to connect without it, because a Node ID nobody resolves is a name and not an address.
  • A ticket carries the addresses, so it works with the lookup off. The CLI publishes one with --invite-ticket, the desktop app grows a setting next to the relay mode, and the Android app accepts a ticket/ invite. Leaving the switch alone keeps n0's lookup, and every client connects exactly as it did.
  • A ticket is an address snapshot: it expires when the server's address changes, and the server prints a fresh one at every start.

Opening a tunnel is measured in the three phases it is made of

  • A slow tunnel used to be one number, which cannot say whether the time went into this process or onto the network. The server now publishes nexapipe_l4_open_duration_ms, nexapipe_l4_route_duration_ms and nexapipe_l4_backend_duration_ms, and the client logs the same split from its own side.

The path a phone's traffic takes got cheaper

  • A packet on the desktop's TUN costs one allocation rather than an allocation and a copy; the TCP window is a credit that grows as the flow carries bytes rather than an allocation taken up front; and the UDP flow table holds a hundred and twenty-eight flows instead of thirty-two.
  • The application's first bytes no longer wait for the server's answer, and the inner MTU is pinned to 1280 — below every valley the path's own MTU probe has shown.
  • A flow socket no longer waits to answer a small message: the peer of a flow socket is the device's own kernel, so Nagle and the delayed ACK cost a local round trip each.

The desktop app is 32% smaller

  • ui-desktop/src-tauri is its own cargo workspace, so the tuning at the root applied to the server crates and to the Android library and to nothing on the desktop: it was built with cargo's defaults, with no LTO and nothing stripped. It has a release profile now.
  • Measured on an Apple M4: the app goes from 39.1 MiB to 26.5 MiB, and the service binary it runs from 19.0 MiB to 12.0 MiB. The cost is build time, and it is measured too — two minutes became three and a half.

Changelog

One line each; the full entry is in CHANGELOG.md.

Added

  • Server: Authenticator — which credential is checked is a seam a deployment can fill with its own, and the built-in check reads the configuration.
  • Server: AccessRecord and AccessSink — the access log as a record a SIEM can take, rather than a line a script has to split.
  • Server: Storage — where the proxy keeps the configuration, the counters and the admin token, with the file behind it and the databases still to come.
  • Server: nexapipe_l4_open_duration_ms, nexapipe_l4_route_duration_ms and nexapipe_l4_backend_duration_ms — the tunnel's opening measured in the three phases it is made of.
  • Clients: a ticket is an address, so a client can reach the server with the address lookup switched off.
  • The three crates are publishable: nexapipe, nexapipe-client and nexapipe-proto are on crates.io.

Changed

  • Desktop: the app is 32% smaller — 39.1 MiB to 26.5 MiB — and the service binary it runs from goes from 19.0 MiB to 12.0 MiB, because the desktop app has a release profile of its own now.
  • Client: a packet on the TUN costs one allocation rather than an allocation and a copy, the TCP window is a credit that grows with the traffic, and the UDP flow table holds a hundred and twenty-eight flows instead of thirty-two.
  • Client: the application's first bytes no longer wait for the server's answer, the inner MTU is pinned to 1280, and a flow socket no longer waits to answer a small message.
  • Android: the native symbols are published beside the APK instead of inside it, so a crash in the field can be debugged without making the download bigger.
  • Release: every artifact's size is recorded by the job that builds it, so a dependency can say what it cost.

Fixed

  • Server: a client that refuses gzip is not answered with it, a stale content-length does not cut the answer, a partial answer is not compressed, and a body the plaintext listener refuses is refused with its own status rather than with a 502 that blames the backend.
  • Server: a WebSocket upgrade the backend refuses carries the backend's body, read under the response budget, and does not forward a header the client marked hop-by-hop.
  • Server: a UDP flow is charged to the process byte budget, and a flow that cannot bind its socket is answered with a status instead of a closed tunnel.
  • Server: a route's own flow bounds are held to the same ceiling as the server-wide ones.
  • Client: a refusal the client made — a full pool, a credential replaced mid-dial — is no longer recorded as a backend failure, and the first write is inside the attempt's budget.
  • Client: a poisoned address map is rebuilt rather than answered with a name that is not there, the UDP flow ceiling is counted instead of walked, and a DNS reply is dropped rather than held.
  • Release: a Linux client gets an update, the assets are published before the index files that name them, a tag that is not the version is refused, and SHA256SUMS.txt is signed.

Before upgrading

The server

  • Nothing has to be changed in the configuration. No key is removed or renamed, no key is added, and every key keeps its meaning. A config.toml that works on 1.0.0 works here unchanged.
  • The store is chosen by the command line or the environment, never by the configuration. --storage wins over NEXAPIPE_STORAGE, and the file backend — the only one this build carries — reads and writes the same files as before. A build without the storage-sqlite or storage-postgres feature says so rather than pretending to open a database it has no driver for.
  • Nothing else changed. The protocol, the ALPN and the L4 preface are the same on the wire, so the clients of 1.0.0 keep working against this server.
  • Docker: pin :1.1.0 rather than :latest if you want the version to stay put.

The clients

  • Nothing to enroll, nothing to rescan. The handshake is unchanged on the wire, and a client that has no device key keeps using its secret.
  • Android: the tunnel's inner MTU is 1280 now. It was 1400, which can sit above the path's own MTU. A rule of your own that hard-codes the old number needs updating; the addresses themselves are unchanged.
  • Desktop: a discovery setting sits next to the relay mode. It is off by default, and leaving it alone keeps n0's address lookup, which is what a client that has never heard of a ticket expects.
  • Desktop: the app and the service are both smaller. Nothing to do: the release profile is the build's business, not the operator's.
